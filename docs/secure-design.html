Secure design

Architecture and design decisions, alternatives and tool justification

This page documents the security-related architecture and design decisions for the routing backend, the alternatives considered, and the justification for chosen tools and mitigations.

1. Design decisions

DecisionRationaleSecurity effect
Single JSON body ceiling (MAX_REQUEST_BODY_BYTES = 1 MiB) on /pathThe handler reads self.rfile.read(length) using the client-supplied Content-Length with no upper bound; a malicious or erroneous client could allocate a multi-gigabyte buffer and exhaust server memory (single process, ThreadingHTTPServer).Caps per-request memory; returns HTTP 413 for oversized bodies.
Reject negative and non-numeric Content-LengthDefensive handling of malformed headers before any allocation.Avoids undefined behaviour and 500 errors on bad input.
Existing per-field validation retainedmax_transfers (≥0), option_count (≥1), departure_time parsing, algorithm whitelist are already validated (http_server.py).Reduces malformed-query attack surface.

2. Alternative mitigation strategies considered

AlternativeProsConsDecision
No change (rely on existing field validation)Zero compatibility riskBody size unbounded; memory-exhaustion vector remainsRejected
Reverse proxy / WAF request-size limit (e.g., nginx client_max_body_size)Offloads concern; operates before the appAdds infrastructure; not part of the repo; doesn't protect direct gRPC accessRecommended for deployment
Application-level body ceiling (implemented)Self-contained, testable, travels with the code; covers direct HTTP accessOnly covers the Python HTTP server, not gRPC or a future reverse proxyImplemented
Per-IP rate limiting + concurrency capsAddresses burst/DoS beyond a single large bodyRequires state store; broader scope than the targeted fixDeferred (future work)

3. Tool justification

  • pytest — standard Python test runner; already the project's test framework (python -m pytest in README).
  • Python standard library http.server — the fix is in the existing handler; no new dependency introduced.
  • Static analysis / dependency scanning — recommended tools: bandit (Python SAST), pip-audit / safety (dependency vulnerabilities). Not installed in the audit environment; documented as a recommended CI step rather than claimed as run.
Scope note. This change addresses the HTTP request path only. The gRPC binding (server.py:305, insecure port), Neo4j credential defaults (config.py:31-34), and pickle deserialization (loader.py) remain as documented risks requiring separate deployment-level controls.
