Threat model

STRIDE analysis of assets, trust boundaries and threat actors

This threat model applies the STRIDE methodology (Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege) to the systems in scope. It identifies trust boundaries, plausible threat actors and representative threats. Each threat is classified as confirmed, potential (requiring verification), configuration-dependent, a general improvement, or informational — consistent with the requirement that a source-code pattern alone does not establish exploitability.

1. Trust boundaries

  • Unauthenticated client → HTTP /path (0.0.0.0:8080).
  • Client → gRPC RouteSearch on [::]:50051 — insecure port, no TLS (src/server.py:305).
  • Backend → Neo4j (env credentials; defaults neo4j/neo4j — src/config.py:31-34).
  • Backend → disk pickle cache — deserialization boundary (loader.py:922, loader.py:598 allow_pickle=True).
  • Backend → external OSRM walking router (outbound HTTP).
  • SwissTransitMap frontend → Express API (CORS-configured).
  • Express API → MongoDB (Mongoose queries).

2. Plausible threat actors

  • Unauthenticated API client — sends crafted HTTP/gRPC requests to the routing service.
  • Network adversary — observes/modifies traffic on insecure HTTP and gRPC bindings.
  • Local user / process — reads or replaces the pickle cache or .env file on the server host.
  • Malicious GTFS / data contributor — ingests crafted stop or timetable records.

No precise CVSS scores are assigned without deployment evidence.
