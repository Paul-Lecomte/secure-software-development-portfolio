Risk register

Prioritised security risks with likelihood, impact and mitigations

This risk register prioritises the security risks identified during the audit. Likelihood and impact are rated qualitatively (Low/Medium/High) with explicit rationale and stated uncertainty. Precise CVSS scores are not assigned where the necessary technical evidence (deployment context, network exposure, exploit conditions) is unavailable.

2. Likelihood and impact rationale

Likelihood reflects how readily the condition can be triggered given the observed code and default deployment (local/localhost dev, unauthenticated endpoints). Impact reflects the consequence for confidentiality, integrity or availability of the assets in Section 3 of the system overview. Where a risk depends on deployment choices (TLS, env values, hosting), it is marked configuration-dependent and no precise CVSS score is assigned.

Uncertainty: The backend is not observed in a deployed production environment, so network exposure, TLS termination, authentication layers and host hardening cannot be confirmed. Ratings assume the service runs as configured in the repository (insecure gRPC port, env-default credentials, no auth middleware).

3. Existing controls and limitations

  • Input validation on max_transfers, option_count, departure_time, algorithm (http_server.py:3106-3140) — limits exist but no hard upper cap on option_count.
  • gRPC/RAPTOR fallback chain (RAPTOR → A* → Dijkstra) improves reliability, not security.
  • OSRM failure backoff and circuit-breaker (_osrm_failure_count, _osrm_disabled_until) limits outbound abuse.
  • Helmet and CORS on the Express API (server.js:22-27) — configuration to verify.

4. Residual risks and future improvements

  • Even with the 1 MiB body ceiling, a burst of many concurrent valid requests could still exhaust CPU/memory (no rate limiting or concurrency caps).
  • gRPC remains on an insecure port unless TLS is deployed.
  • No audit logging of request origin or user identity.
  • Neo4j credentials must be injected via environment; defaults must never be used in production.
