2. System scope and architecture

Primary case study — Python routing backend (fastest_path_backend)

A high-performance public-transit route-planning microservice using the RAPTOR algorithm with NumPy/Numba acceleration. It loads GTFS-like transit data (optionally from Neo4j, with a disk cache and a mock-network fallback) and exposes earliest-arrival path searches over two network bindings:

  • HTTP — ThreadingHTTPServer on 0.0.0.0:8080, single endpoint POST /path (source: src/http_server.py).
  • gRPC — asynchronous gRPC server on [::]:50051, service RouteSearch, method GetFastestPath (source: src/server.py, proto proto/pathfinding.proto).

Key modules: src/config.py (env + Neo4j config), src/loader.py (Neo4j load + pickle cache), src/solver.py (RAPTOR/Dijkstra/A*), tests/test_smoke.py (26 tests).

Supporting system — SwissTransitMap (swiss-pb-map)

Full-stack Swiss public-transport visualization and route-planning app. Frontend: Next.js 16 / React 19 / TypeScript / Leaflet. Backend: Node.js / Express on port 3000/4000. Database: MongoDB via Mongoose. Uses JWT (jsonwebtoken) and bcrypt, Helmet, CORS, morgan. Calls the Python backend for fastest-path computation. GTFS ingestion pipelines load stops, routes, trips and stop times into MongoDB.

4. Trust boundaries

  • Client → HTTP endpoint (/path): unauthenticated, network-exposed.
  • Client → gRPC endpoint (:50051): insecure port, no TLS (src/server.py:305).
  • Backend → Neo4j: database access using env-configured credentials.
  • Backend → disk pickle cache (.cache/transit_network.pkl): deserialization boundary (loader.py:922, loader.py:598 with allow_pickle=True).
  • SwissTransitMap frontend → Express API: CORS-configured cross-origin boundary.
  • Express API → MongoDB: query boundary (Mongoose).
  • Backend → external OSRM walking service (outbound HTTP).
