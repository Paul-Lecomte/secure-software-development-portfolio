1. Introduction

This activity explores two important programming language concepts: recursion and regular expressions (regex).

The first exercise investigates recursion through the classic Towers of Hanoi problem. It demonstrates how a complex problem can be divided into smaller problems using recursive function calls, while also highlighting computational complexity and potential security implications.

The second exercise focuses on regular expressions through the implementation of a UK postcode validator. It explores how regex can be used to validate structured input and examines the security risks associated with poorly designed expressions, particularly Regular Expression Denial of Service (ReDoS).

The activity concludes with an analysis of how these programming concepts relate to application and system security.

2. Exercise 1 – Recursion: Towers of Hanoi

2.1 Understanding Recursion

Recursion is a programming technique in which a function calls itself to solve a problem. Instead of solving the entire problem in one operation, the function breaks it down into smaller instances of the same problem.

A recursive function generally consists of two important components:

  • Base case: Defines the condition under which recursion stops.
  • Recursive case: Calls the function again with a smaller or simpler input.

The Towers of Hanoi is a classic example of recursion. It involves three pegs and a number of disks of different sizes.

The objective is to move all disks from the source peg to the destination peg while following three rules:

  1. Only one disk can be moved at a time.
  2. Only the uppermost disk of a peg can be moved.
  3. A larger disk cannot be placed on top of a smaller disk.

Recursive approach

The problem can be divided into three steps:

  1. Move the top \(n-1\) disks from the source peg to the auxiliary peg.
  2. Move the largest remaining disk from the source peg to the destination peg.
  3. Move the \(n-1\) disks from the auxiliary peg to the destination peg.

The recurrence relation is:

\(T(n)=2T(n-1)+1\)

Solving this recurrence gives:

\(\boxed{T(n)=2^n-1}\)

This means that the minimum number of moves grows exponentially with the number of disks.

2.2 Python Implementation

The following implementation uses a recursive function to solve the Towers of Hanoi problem. It asks the user for the number of disks, executes the moves and displays the total number of moves.

def towers_of_hanoi(n, source, destination, auxiliary):
    """
    Recursively solves the Towers of Hanoi problem.
    Returns the total number of moves performed.
    """

    # Base case
    if n == 0:
        return 0

    # Step 1: Move n-1 disks to the auxiliary peg
    moves = towers_of_hanoi(
        n - 1, source, auxiliary, destination
    )

    # Step 2: Move the largest remaining disk
    print(f"Move disk {n} from {source} to {destination}")
    moves += 1

    # Step 3: Move n-1 disks to the destination peg
    moves += towers_of_hanoi(
        n - 1, auxiliary, destination, source
    )

    return moves


def main():
    try:
        disks = int(input("Enter the number of disks: "))

        if disks < 1:
            print("Please enter a positive integer.")
            return

        print("\nStarting Towers of Hanoi...\n")

        total_moves = towers_of_hanoi(
            disks, "A", "C", "B"
        )

        print("\nCompleted!")
        print(f"Number of disks: {disks}")
        print(f"Total moves executed: {total_moves}")

    except ValueError:
        print("Invalid input. Please enter an integer.")


if __name__ == "__main__":
    main()

Explanation

The towers_of_hanoi() function receives four parameters:

  • n: Number of disks remaining.
  • source: Original peg.
  • destination: Target peg.
  • auxiliary: Temporary peg.

The base case is n == 0, which stops further recursive calls.

Otherwise, the function calls itself twice to move the smaller disks before and after moving the largest remaining disk.

The function returns the total number of moves, avoiding the need for a global counter.

2.4 What Is the Theoretical Maximum Number of Disks?

There is no single universal maximum number of disks that Python can process. The practical limit depends on the interpreter configuration and available system resources.

Two main limitations must be considered.

1. Python recursion limit

Python imposes a maximum recursion depth to protect the interpreter's call stack.

The current recursion limit can be inspected using:

import sys

print(sys.getrecursionlimit())

A typical Python installation has a default recursion limit of approximately 1,000 calls.

Since each recursive call reduces the number of disks by one, attempting to process too many disks can result in a RecursionError.

The exact maximum number of disks is lower than or equal to the available recursion depth, depending on other function calls already occupying the stack.

2. Computational resources

Even if the recursion limit is increased, the number of moves becomes impractical very quickly.

For example, 30 disks require more than one billion moves. Printing each move would generate an enormous quantity of output and consume considerable processing time.

Therefore, the theoretical number of disks is not the same as the practical number that a computer can process efficiently.

2.5 What Limits the Number of Iterations and What Are the Security Implications?

The number of operations is determined by the recursive structure:

\(T(n)=2T(n-1)+1\)

Which produces:

\(T(n)=2^n-1\)

The main limitations include:

  • Recursion depth: Excessive nested function calls can cause a RecursionError.
  • CPU consumption: Exponentially increasing operations can consume significant processing resources.
  • Memory consumption: Every active recursive call requires memory for its execution context.
  • Output consumption: Printing every operation can generate excessive output and potentially exhaust storage resources.
Security implications

This problem demonstrates how a program can be logically correct but still introduce security vulnerabilities through uncontrolled resource consumption.

If an application accepts an unrestricted number of disks from an external user, an attacker could submit an extremely large value to trigger computationally expensive operations.

If such requests are repeatedly submitted, the application could become unresponsive to legitimate users.

This is an example of a potential Denial of Service (DoS) vulnerability.

Possible mitigation strategies include:

  • Validate and restrict user input.
  • Establish reasonable limits on computationally expensive operations.
  • Apply execution timeouts where appropriate.
  • Monitor CPU and memory consumption.
  • Avoid generating unnecessary output.
  • Consider iterative implementations when recursion is not necessary.

The main lesson is that developers must consider resource consumption when designing algorithms that process externally supplied input.

3. Exercise 2 – Regular Expressions: UK Postcode Validation

3.1 Understanding Regular Expressions

Regular expressions are patterns used to identify, search and validate strings.

They are commonly used for input validation, data extraction, text processing and security-related filtering.

For this exercise, the objective is to implement a Python program that checks whether a string follows the UK postcode format.

An important distinction is that a regex can verify whether a postcode follows the expected structure, but it cannot independently guarantee that the postcode actually exists.

UK postcode structure

A UK postcode consists of two main parts:

  • Outward code: Identifies the postcode area and district.
  • Inward code: Identifies a more specific delivery location.

Examples of valid postcode structures include:

Format Example
A9 9AAM1 1AA
A99 9AAM60 1NW
AA9 9AACR2 6XH
AA99 9AADN55 1PT
A9A 9AAW1A 1HQ
AA9A 9AAEC1A 1BB

The final two letters of the inward code cannot contain C, I, K, M, O or V.

This explains why ST7 9HV is invalid: its final character is V.

3.2 Python Implementation

The following implementation uses a regular expression to validate the permitted UK postcode structures, including the special postcode GIR 0AA.

import re

# UK postcode format, including the special GIR 0AA postcode.
POSTCODE_PATTERN = re.compile(
    r"^(?:GIR 0AA|"
    r"(?:"
    r"[A-PR-UWYZ][0-9]{1,2}|"
    r"[A-PR-UWYZ][A-HK-Y][0-9]{1,2}|"
    r"[A-PR-UWYZ][0-9][A-HJKSTUW]|"
    r"[A-PR-UWYZ][A-HK-Y][0-9][ABEHMNPRV-Y]"
    r") "
    r"[0-9][ABD-HJLNP-UW-Z]{2}"
    r")$"
)


def validate_postcode(postcode):

    # Normalise input
    postcode = postcode.strip().upper()

    # Reject excessively long input
    if len(postcode) > 8:
        return False

    # Match the entire string against the pattern
    return POSTCODE_PATTERN.fullmatch(postcode) is not None


def main():

    postcode = input("Enter a UK postcode: ")

    if validate_postcode(postcode):
        print(f"{postcode.upper()} follows the UK postcode format.")
    else:
        print(f"{postcode} is not a valid UK postcode format.")


if __name__ == "__main__":
    main()

Explanation of the regex

Regex component Explanation
^Beginning of the string
GIR 0AASpecial postcode exception
[A-PR-UWYZ]Permitted first letter of the outward code
[0-9]{1,2}One or two digits
[A-HK-Y]Permitted second letter in a two-letter area
[A-HJKSTUW]Permitted letter in the special outward-code format
[ABEHMNPRV-Y]Permitted final letter of certain outward codes
SpaceSeparates outward and inward codes
[0-9]First character of the inward code
[ABD-HJLNP-UW-Z]{2}Two permitted final letters
$End of the string

The expression uses explicit character ranges to restrict which characters are accepted.

Limitations

This implementation validates the postcode format, not the existence of a postcode.

A postcode can match the regular expression while not being officially assigned or currently active.

For production applications, a postcode validation service or authoritative postcode database can provide an additional verification layer.

4. Evil Regex and Application Security

4.1 What Is Evil Regex?

Evil Regex refers to a regular expression that can cause extremely inefficient processing when presented with specially crafted input.

This is commonly associated with an attack known as Regular Expression Denial of Service (ReDoS).

Some regex engines use a backtracking mechanism. When a match fails, the engine may revisit previous positions and attempt alternative matching paths.

Certain expressions can create an enormous number of possible paths, causing processing time to increase exponentially with input length.

Consider the following example:

import re

pattern = re.compile(r"^(a+)+$")

print(pattern.match("aaaaaaaaX"))

The expression contains nested repetition.

When the input contains many a characters followed by an invalid character such as X, the regex engine may explore many different ways of dividing the repeated characters into groups before determining that the match fails.

An attacker could exploit this behaviour by submitting specially constructed input to a vulnerable application.

For example:

  1. An application uses a vulnerable regex to validate usernames.
  2. An attacker discovers the regex pattern.
  3. The attacker submits carefully constructed input.
  4. The regex engine performs an excessive number of matching operations.
  5. The application becomes slow or unresponsive.

This can prevent legitimate users from accessing the service.

4.2 What Are the Common Problems Associated with Regex and How Can They Be Mitigated?

There are several problems developers need to consider when implementing regular expressions.

Problem Explanation Mitigation
ReDoS attacks Certain patterns cause excessive backtracking and CPU consumption. Avoid nested quantifiers and overlapping alternatives. Use execution limits where available.
Complex expressions Long and complicated patterns are difficult to understand and maintain. Keep expressions simple, document them and split complex validation into smaller steps.
Incorrect validation A regex might accept invalid data or reject valid data. Test against valid and invalid examples and maintain a comprehensive test suite.
Regex injection Untrusted input inserted into a regex can change its behaviour. Escape user-supplied literals and avoid constructing regex patterns from untrusted input.
Excessively long input Large inputs can increase processing time and memory consumption. Apply input length restrictions before regex evaluation.
Engine differences Different regex engines can interpret certain features differently. Use well-supported syntax and test using the actual target engine.

Mitigation strategies

A secure implementation should follow several principles:

  • Prefer simple and predictable expressions.
  • Avoid nested repetition such as (a+)+.
  • Avoid overlapping alternatives that create excessive backtracking.
  • Limit the length of user-provided input.
  • Use regex timeout functionality where the language or library supports it.
  • Never assume client-side validation is sufficient; repeat validation on the server.
  • Use automated testing, including malicious and unexpected inputs.

For applications processing untrusted input at scale, developers can also consider regex engines with guaranteed linear-time matching, such as Google's RE2, rather than relying on a backtracking engine.

In the postcode implementation, the risk is reduced through a predefined expression, explicit character ranges, a maximum input length and full-string matching.

The pattern does not contain nested quantifiers or ambiguous repeated alternatives.

4.3 How and Why Could Regex Be Used as Part of a Security Solution?

Regular expressions can contribute to application security by helping developers identify, validate and filter input.

There are several useful applications.

1. Input validation

Regex can verify that data follows an expected format before an application processes it.

Examples include:

  • Email address format checking.
  • Postcode validation.
  • Username restrictions.
  • Password policy checks.
  • Identification number formatting.

This helps reduce malformed or unexpected input entering an application.

2. Detecting suspicious activity

Regex can be used to search application logs for suspicious patterns.

For example, a security monitoring system could look for repeated SQL injection indicators, unexpected request patterns or suspicious authentication attempts.

3. Security filtering

Regex can help identify potentially dangerous input, including suspicious script fragments or known attack signatures.

However, regex-based filtering should not be considered a complete defence against attacks such as SQL injection or Cross-Site Scripting (XSS).

Dedicated protections should be used, such as:

  • Parameterised SQL queries.
  • Context-aware output encoding.
  • Established security libraries.
4. Enforcing security policies

Regex can help enforce consistent input requirements, such as:

  • Restricting usernames to permitted characters.
  • Enforcing password complexity requirements.
  • Checking that identifiers follow an expected structure.
  • Validating file naming conventions.
Critical analysis

Although regex can be useful as a security mechanism, it must be implemented carefully.

A poorly designed validation expression could itself introduce a vulnerability, particularly ReDoS.

Additionally, matching a string against a pattern does not necessarily establish that the data is safe.

For example, a postcode regex can establish that an input follows the expected postcode structure, but it cannot guarantee that the postcode exists.

Similarly, identifying a potentially malicious string does not necessarily mean that the application is protected against the underlying vulnerability.

Therefore, regex should be considered one component of a broader security strategy rather than a standalone security solution.

5. Reflection and Learning Outcomes

The two exercises demonstrate different aspects of programming language concepts and their relationship with software security.

The Towers of Hanoi exercise helped me understand how recursion can simplify problems by breaking them down into smaller versions of the same problem. However, it also demonstrated that recursive algorithms can introduce performance and resource limitations.

The exponential growth in the number of operations means that an algorithm can become impractical even when its implementation is logically correct.

The regular expression exercise demonstrated how patterns can be used to validate structured input. It also highlighted the importance of understanding how regex engines process expressions, particularly when dealing with untrusted input.

One important distinction I identified is that validating the structure of information does not necessarily establish its actual validity. For example, a postcode can match the expected format without corresponding to an existing address.

Overall, these activities demonstrated that programming language concepts should be evaluated not only in terms of functionality and correctness but also in terms of performance, reliability and security.
