Assignment: Buffer Overflow Vulnerability and Stack Protection Analysis

Lab Report — Exploring Python Tools and Features (Part 1)

1. Objective

The purpose of this experiment is to observe the mechanics of a stack-based buffer overflow vulnerability in C/C++, understand how excess input corrupts control flow in un-protected binaries, and verify the effectiveness of compiler-level stack protection mechanisms (/GS stack canary).

2. Test Execution & Results

Test Case Configuration Input Input Length Expected vs. Observed Outcome Result
Test 1 MSVC (No Protection / /GS-) Alex 4 chars (≤ 8) Normal execution; input printed back correctly. PASS
Test 2 MSVC (No Protection / /GS-) AAAAAAAAAA 10+ chars (≥ 10) Buffer overflow; program crashes with an Access Violation. FAIL (Vulnerable)
Test 3 (Bonus) MSVC (With Protection / /GS) AAAAAAAAAA 10+ chars (≥ 10) Abrupt controlled termination; stack canary detects tampering. PROTECTED

3. Analysis & Findings

3.1 Unprotected Execution Analysis (/GS-)

When the program was compiled without stack protection, memory allocation for buf was strictly restricted to 8 bytes on the stack.

  • Short Input (Alex): The input fits entirely within the allocated 8-byte array bounds, maintaining stack integrity.
  • Long Input (AAAAAAAAAA): Input exceeding 8 bytes overflows the boundaries of buf[8]. The extra ASCII characters overwrite adjacent stack memory structures, specifically:
    1. The Saved Frame Pointer (EBP/RBP)
    2. The Return Address (EIP/RIP)

3.2 Output Explanation

When entering 10+ characters under /GS-, the program fails with an Access Violation (or segmentation fault).

  • Underlying Cause: The ASCII input character A (hexadecimal 0x41) overwrites the saved return address on the stack.
  • Execution Failure: When main() finishes executing and attempts to return, the CPU pops the corrupted stack memory into the instruction pointer register. The CPU attempts to execute instructions located at the invalid address (e.g., 0x4141414141414141). Because this address does not belong to an executable memory page allocated to the process, the operating system halts execution immediately to prevent erratic behavior.

4. Protection Comparison (/GS Stack Canary)

Re-compiling and executing the long input with MSVC's standard stack protection (/GS) changed the outcome significantly:

  • Mechanism: The compiler places a randomized security cookie (stack canary) on the stack between local buffers (like buf) and the saved return address.
  • Observation: Upon entering AAAAAAAAAA, the canary value was overwritten before the return address could be reached.
  • Outcome: Prior to returning from the function, the compiler's inserted check detected the modified canary and triggered an immediate, controlled termination with a safety message (Stack buffer overflow detected!). This prevented execution from jumping to the corrupted address, mitigating potential arbitrary code execution.

5. Conclusion

This lab demonstrates that unsafe memory handling in statically allocated buffers can easily lead to control-flow corruption. While modern compilers provide built-in mitigation techniques such as stack canaries (/GS), developer best practices (e.g., bounds checking and using safe string functions) remain essential for writing secure software.
